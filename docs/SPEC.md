# fable-handoff: build specification

This is the contract for the `fable-handoff` skill. `tests/` holds the
acceptance suite that checks it. Where this document and the tests disagree,
the tests win, and the disagreement should be reported.

## 1. What the skill is for

A Claude skill that a preparing agent follows to get a software project ready
for Claude Fable 5.2 to take over and finish in one long unattended run, with
no human available. The agent prepares; Fable executes; the owner answers
questions once, before launch.

Three facts about Fable 5.2 drive the design (details in
`inputs/fable-5-2-facts.md`):

1. It applies instructions almost literally, so stale rules stall a run.
2. It is strongest when given a whole outcome and the reason, not steps.
3. Nobody is there, so every question must be answered in advance, "done"
   must be checkable by a program, and hard limits must be enforced by code.

## 2. Layout of the skill

```
fable-handoff/
  SKILL.md
  references/            at least three .md files, each named in SKILL.md
  scripts/
    init_handoff.py
    audit_rules.py
    readiness_check.py
    post_run_report.py
  assets/
    templates/  MISSION.md  OPERATING_RULES.md  STATE.md  DECISIONS.md  launch.py
    hooks/      fable_guard.py  fable_stop_gate.py  fable_session_context.py
    agents/     fable-scout.md  fable-builder.md
```

All Python is standard library only, runs on Python 3.9+, and works with
`python3 script.py` and `uv run script.py`. No em dashes anywhere in the skill.

## 3. What the skill installs in a project

| Path in the project | Source |
| --- | --- |
| `fable/handoff.json` | generated by init |
| `fable/MISSION.md`, `fable/STATE.md`, `fable/DECISIONS.md` | templates, with `{{FILL: ...}}` markers |
| `fable/OPERATING_RULES.md` | template, no markers left after init |
| `fable/launch.py` | template |
| `.claude/hooks/fable_guard.py`, `fable_stop_gate.py`, `fable_session_context.py` | hooks |
| `.claude/agents/fable-scout.md`, `fable-builder.md` | agents |
| `.claude/settings.json` | merged |

Written during a run by the model: `fable/REPORT.md`, `fable/BLOCKED.md`.
Run artifacts live in `fable/.run/` (gitignored).

## 4. SKILL.md

Frontmatter: `name: fable-handoff` and a `description` of 200 to 1024
characters that says what the skill does and when to use it, written to
trigger readily (handing a project to Fable, long-horizon or overnight or
walk-away runs, autonomous completion, mission brief, handoff package, making
CLAUDE.md or skills safe for Fable 5.2, reviewing an unattended run). No angle
brackets in the description. Under 500 lines in total.

The body instructs the preparing agent, in imperative voice, explaining the
reason behind each instruction. It must cover these phases in order:

0. Decide whether this is a Fable job (long, open-ended, beyond Opus at high).
1. Discover: read the project and every instructions file that will load, run
   the build and test commands, report understanding to the owner.
2. Interview the owner once: outcome, why, scope edges, authority, every
   irreversible action sorted into pre-approved, forbidden or skip-and-leave,
   limits, traps. Record in DECISIONS.md.
3. Make "done" checkable: one verify command that fails now, passes only when
   the mission is complete, runs without a person, and cannot be satisfied by
   deleting tests.
4. Scaffold with `init_handoff.py`, then tune `handoff.json`.
5. Clean up instructions with `audit_rules.py`; rewrite FIX findings, judge
   REVIEW findings; scope interactive-only rules instead of deleting them;
   propose rather than apply edits outside the project.
6. Write the mission and seed the ledger.
7. Prove readiness with `readiness_check.py`, then read the mission cold.
8. Launch with `fable/launch.py` and hand back.
9. Review with `post_run_report.py` and the diff.

It names every script and `launch.py`, and points at each reference file with
a note on when to read it.

## 5. Reference files

At least: one on how Fable 5.2 behaves and what each behavior means for a
handoff (from `inputs/fable-5-2-facts.md`); one on writing the mission, with
weak and strong examples for each section and one complete sample mission; one
on Claude Code setup (permission modes, hooks, settings placement, launcher,
`handoff.json` keys, troubleshooting; from `inputs/claude-code-facts.md`).
Files over 100 lines start with a table of contents.

## 6. Templates

**MISSION.md** has the headings `## Job`, `## Why`, `## Where things are`,
`## Guardrails`, `## Decisions`, `## Done`, with `{{FILL: ...}}` markers that
explain what belongs in each place. Guardrails has three lists: pre-approved,
forbidden (enforced by hook), out of scope. Done lists: every task in
`fable/STATE.md` checked, the verify command exits 0, `fable/REPORT.md`
written; and tells the model to stop when these hold.

**OPERATING_RULES.md** is appended to the system prompt. In the skill's own
words it tells the model: the run is unattended and questions reach nobody;
keep working until the mission is delivered; work through ordinary obstacles
(errors, timeouts, failing tools) and leave deliberate blockers alone (guard
blocks, forbidden paths, withheld access); when nothing can move without the
owner, write `fable/BLOCKED.md` and the report; keep `fable/STATE.md` current
and commit per task; record decisions in `fable/DECISIONS.md`; report only
what was run and observed; what a subagent costs and when one is worth it,
preferring `fable-scout` and `fable-builder`; write `fable/REPORT.md` for a
reader with no context. It must not ask for step-by-step or written-out
reasoning. It ends with a `{{OWNERSHIP_BLOCK}}` marker that init replaces
with an ownership paragraph (containing "codebase is yours") or with nothing.

**STATE.md** has current focus, next step, a task checklist (`- [ ]` items
with FILL markers) and notes for a resuming session.

**DECISIONS.md** has `## Made before the run`,
`## Defaults for anything not listed`, `## Open questions for the owner`,
`## Made during the run`, `## Left for the owner`.

**Agents**: Markdown with frontmatter `name`, `description`, `model`.
`fable-scout` is read-only search on `haiku`. `fable-builder` implements a
written brief on `opus` or `sonnet`.

## 7. handoff.json

Keys written by init: `version`, `model` (default `fable`), `effort`
(`high`), `permission_mode` (`auto`), `branch`, `verify_command`,
`verify_timeout_seconds` (1800), `ownership`, `protected_paths`,
`blocked_bash_patterns`, `allow_writes_outside_project` (false),
`max_stop_blocks` (8), `max_total_stop_blocks` (60), `max_relaunches` (3),
`max_budget_usd`, `max_turns` (null), `audit_accept` ([]), `extra_cli_args`
([]). Optional: `claude_binary`.

Default `protected_paths` include `.env`, `.env.*`, `*.pem`, `*.key`,
`.git/**`, `.claude/settings.json`, `.claude/settings.local.json`,
`.claude/hooks/**`, `fable/handoff.json`, `fable/MISSION.md`,
`fable/OPERATING_RULES.md`, `fable/launch.py`.

Default `blocked_bash_patterns` (regex, case-insensitive) cover: force push,
push to main or master or production, `git reset --hard`, `git clean -f`,
`rm -rf` of `/`, `~` or `$HOME`, curl or wget piped to a shell, `sudo`,
terraform or pulumi apply or destroy, kubectl apply or delete, package
publishing, SQL `DROP TABLE|DATABASE|SCHEMA`.

## 8. scripts/init_handoff.py

`--project` (required), `--verify-command`, `--verify-timeout`, `--branch`,
`--model`, `--effort`, `--permission-mode`, `--max-budget-usd`, `--ownership`,
`--force`.

- Creates the eleven files of section 3 (settings excluded). Existing files
  are left alone and listed as skipped unless `--force`.
- Merges into `.claude/settings.json`, preserving every existing key, after
  writing a backup `settings.json.bak-<timestamp>` when the file existed:
  a `PreToolUse` group with matcher `Bash|Write|Edit|MultiEdit|NotebookEdit`,
  a `Stop` group and a `SessionStart` group, each a command hook of the form
  `python3 "${CLAUDE_PROJECT_DIR}/.claude/hooks/<name>"`; the Stop hook's
  `timeout` is the verify timeout plus 120; `permissions.deny` gains
  `Read(./.env)` and `Read(./.env.*)`. Running twice adds nothing twice.
- Invalid JSON in existing settings: exit non-zero and leave the file as is.
- Appends `fable/.run/` to `.gitignore` once.
- `--refresh-hooks` updates only the code that came from the skill, in a
  project that already has a package: the three hook files and
  `fable/launch.py` are overwritten and listed under `created`. The mission,
  operating rules, ledger, decisions, `handoff.json`, agents and settings are
  not touched. Without an existing `fable/handoff.json` it exits non-zero and
  creates nothing.
- Prints JSON: `project`, `created`, `skipped_existing`, `settings_added`,
  `backups`. Exit 0.

## 9. scripts/audit_rules.py

`--project` (required), `--extra PATH...`, `--json`, `--out FILE`, `--strict`.

Scans `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` at any depth and Markdown
under any `.claude/` directory, plus `--extra` files or directories. Skips
`.git`, `node_modules`, virtualenvs, build output, the `fable/` directory and
the agents this skill installs. Ignores lines inside fenced code blocks.

Rule ids and severities:

| id | severity | catches |
| --- | --- | --- |
| `think-less` | FIX | "answer directly", "don't overthink" |
| `reasoning-out` | FIX | "think step by step", "explain your reasoning" |
| `needs-human` | FIX | "wait for approval", "do not implement until approved", "stop and ask" |
| `absolute` | REVIEW | never, always, must not, under no circumstances |
| `delegation` | REVIEW | standing orders to use or spawn subagents |
| `style-cap` | REVIEW | word, sentence or line limits |
| `token-budget` | REVIEW | a token budget stated in the prompt |
| `vague-autonomy` | REVIEW | "be proactive", "use your best judgment" |
| `answer-is-done` | REVIEW | "treat that answer as done" |
| `asks-human` | REVIEW | "ask me when unclear", "check with the user" |

Each finding: `file` (relative to the project when inside it), `line`, `rule`,
`severity`, `match`, `text`, `why`, `fix`, `accepted`. A finding is accepted
when `"<file>:<rule>"` is in `audit_accept` in `fable/handoff.json`.

`--json` prints `{"files": [...], "findings": [...]}`. Otherwise a Markdown
report with each finding as `` `file:line` [rule] text `` followed by why and
what to write instead; `--out` writes the same Markdown to a file. Exit 0,
except 1 with `--strict` when an unaccepted FIX finding exists.

## 10. Hooks

Each reads the hook payload as JSON on stdin and locates the project from
`CLAUDE_PROJECT_DIR`, then the payload's `cwd`, then the working directory.
Exit 0 lets the action proceed. Exit 2 blocks it and stderr goes to the model.
Each does nothing (exit 0, no output) when `fable/handoff.json` is absent.

**fable_guard.py** (PreToolUse). For `Write`, `Edit`, `MultiEdit`
(`tool_input.file_path`) and `NotebookEdit` (`notebook_path`): block when the
path, relative to the project, matches a protected glob, or lies outside the
project unless `allow_writes_outside_project`. Globs are gitignore style:
`**` crosses directories, `*` stays in a segment, a pattern without a slash
matches at any depth, and a match on a directory covers everything under it.
For `Bash` (`tool_input.command`): block when the command matches a blocked
pattern, or when it would write to, move or delete a protected path: the
target of a redirect or `tee`, an argument of `rm`, `mv`, `chmod`, `truncate`,
`touch` and similar, the destination of `cp`, the file of `sed -i`, or the
paths of `git checkout|restore|rm|mv`. Reading a protected file, copying it
elsewhere, or merely mentioning its name (in a commit message, a grep pattern,
or the body of a heredoc) is not a write. Redirects to `/dev/null` or between
file descriptors are not writes. This is a text heuristic, not a shell parser.

Two refinements keep the guard from blocking harmless work, because every
false block costs an unattended run a detour:

- *Directory changes are followed.* A `cd <dir>` earlier in the same command
  changes the directory that later relative paths are resolved against, so
  `cd /tmp/other && echo x > fable/MISSION.md` is not a write to this project,
  and `cd fable && rm MISSION.md` is.
- *Quoted text and heredoc bodies are data, not commands.* A blocked pattern or
  a protected path that appears only inside a quoted string containing
  whitespace (a commit message, an `echo` or `grep` argument) or inside a
  heredoc body is a mention and does not block. The exception is text handed
  to a shell to run: the argument of `bash -c`, `sh -c`, `zsh -c` or `eval`,
  and a heredoc fed to `bash`, `sh` or `zsh`, are checked as commands. A
  quoted single word such as `"$HOME"` or `"main"` is still an argument and
  is checked. Other tools pass. A config that
cannot be parsed blocks (fail closed). The block message says this is a
deliberate blocker, not to work around it, to note it in
`fable/DECISIONS.md`, and to continue with other work.

**fable_stop_gate.py** (Stop). In order: `fable/BLOCKED.md` with non-blank
content allows the stop. Unchecked tasks in `fable/STATE.md` block, listing
them. With no tasks open, run `verify_command` (shell, project root,
`verify_timeout_seconds`); a failure blocks and shows the command and the tail
of its output. A missing or empty `fable/REPORT.md` blocks. Otherwise allow.
Each block is counted in `fable/.run/stop_gate.json`: `consecutive` resets
when the number of open tasks or the verify result changed since the last
block. When `consecutive` exceeds `max_stop_blocks` or the total exceeds
`max_total_stop_blocks`, allow the stop and write
`fable/.run/stop_gate_exhausted.txt` with the reasons. With
`FABLE_GATE_DRY_RUN=1` nothing is written. Empty or invalid stdin is treated
as an empty payload. The verify command is run without `FABLE_GATE_DRY_RUN` in
its environment, so a test suite that itself runs a stop gate is not switched
into dry-run mode.

**fable_session_context.py** (SessionStart). Prints a short note naming
`fable/MISSION.md`, `fable/STATE.md` and `fable/DECISIONS.md`, the payload's
`source`, and the ledger count as "<n> done, <m> remaining".

## 11. scripts/readiness_check.py

`--project` (required), `--extra PATH...`, `--allow-dirty`,
`--allow-passing-baseline`, `--json`.

Runs all checks and reports rows of `status` (PASS, WARN, FAIL), `check`,
`detail`. `--json` prints `{"ok": bool, "rows": [...]}`; otherwise an aligned
table and a final line starting `READY` or `NOT READY`. Exit 0 only when no
row is FAIL. Writes `fable/.run/readiness.json` with `ok`, `checked_at`,
`package_hash`, `base_commit`, `baseline` (`command`, `exit_code`, `seconds`)
and `rows`. `package_hash` is the SHA-256 over, in this order, for each of
`MISSION.md`, `OPERATING_RULES.md`, `handoff.json` in `fable/`: the file name
bytes, then the file bytes. It leaves the working tree clean and does not
count as a stop-gate block.

Check names and what fails them:

| check | FAIL when |
| --- | --- |
| `config` | `handoff.json` missing, invalid, missing keys, or holding an invalid regex |
| `mission` | file missing; a `{{FILL` marker; a required section (Job, Why, Guardrails, Decisions, Done) missing or empty; Job under 40 words; Why under 20 words; wording that assumes a human ("ask me", "wait for my approval"); the verify command not quoted in the file. HTML comments are ignored |
| `operating rules` | missing or still holding a `{{` marker |
| `ledger` | missing, a FILL marker, or no unchecked task |
| `decisions` | missing, a FILL marker, or "Open questions for the owner" not reading `None.` |
| `git branch` | not a repo, or on main, master, production, prod or release |
| `git clean` | uncommitted changes (WARN with `--allow-dirty`) |
| `secrets` | git tracks `.env` (not `.env.example|sample|template`), `*.pem`, `*.p12`, `id_rsa`, `id_ed25519`, `credentials.json` |
| `verify` | command empty, cannot execute (exit 126 or 127), times out, or already passes (WARN with `--allow-passing-baseline`) |
| `hooks installed` | a hook file is missing |
| `hooks registered` | a hook is not referenced in `.claude/settings.json` |
| `guard self-test` | the guard gives the wrong exit code for synthetic payloads: a protected path, a path outside the project, an ordinary file, a force push, a harmless command |
| `stop gate self-test` | the gate (dry run) does not block while tasks are open |
| `session context self-test` | the hook fails or does not name the mission |
| `rules audit` | an unaccepted FIX finding; the detail names file and line |

WARN rows (never failing): a row named `mission wording` when the mission
uses "never" or "always" as a directive (at the start of a sentence or list
item, or after "must", "should" or "you"), with the detail quoting each such
line, and no such row, or a PASS row, when the words are only descriptive
("has never seen", "was always slow"); effort below high or above high;
`bypassPermissions`; no `max_budget_usd`; branch differs from the config; a
project agent without a pinned model (detail names the file); REVIEW findings
from the audit; the CLI binary missing.

## 12. fable/launch.py

`--dry-run`, `--skip-readiness`. Works from its own location (the project is
the parent of `fable/`).

- Refuses (exit 2, message on stderr, nothing started) unless
  `fable/.run/readiness.json` has `ok` true and a `package_hash` equal to the
  current one. This applies to `--dry-run` as well.
- Command: `<claude_binary or "claude"> -p <mission text> --model M --effort E
  --permission-mode P --append-system-prompt-file fable/OPERATING_RULES.md
  --output-format stream-json --verbose`, plus `--max-budget-usd <amount with
  two decimals>` when a cap is set, `--max-turns N` when set, then
  `extra_cli_args`.
- `--dry-run` prints that command with the mission replaced by a short
  placeholder and exits 0.
- Each launch writes stdout to `fable/.run/transcript-<n>.jsonl` and stderr
  to `stderr-<n>.log`, and appends to `launch_log.json` an entry with
  `attempt`, `mode` (`fresh` or `continue`), `exit_code`, `seconds`,
  `budget_usd`, `finished`, `blocked`.
- After each exit: `blocked` when `fable/BLOCKED.md` has content; `finished`
  when not blocked and the stop gate (dry run) allows a stop.
- Unfinished and not blocked: relaunch, up to `max_relaunches` extra times.
  After exit 0, add `--continue` and send a short resume prompt that names
  `fable/STATE.md` and does not repeat the mission. After a non-zero exit,
  start fresh with the resume prompt followed by the full mission.
- Budget: each launch receives the cap minus the sum of the `total_cost_usd`
  values in the `result` lines of earlier transcripts. No launch starts when
  nothing is left.
- Before the first launch of an invocation, an existing `fable/REPORT.md` is
  moved to `fable/.run/REPORT-previous-<timestamp>.md`. A report left from an
  earlier run would otherwise satisfy the stop gate before any work is done.
  A report written during the invocation is left in place.
- Exit 0 finished, 1 unfinished, 2 refused, 3 stopped on a recorded blocker.

## 13. scripts/post_run_report.py

`--project` (required), `--out FILE`, `--skip-verify`.

Prints a Markdown review whose verdict line contains `CLEAN` or
`NEEDS REVIEW` followed by the reasons; `--out` writes the same text. Exit 0
only when clean. It re-runs the verify command (unless skipped) and shows the
command and result; compares against `base_commit` from the readiness record
and lists changed files; and reports as problems: unchecked tasks ("task"), a
failing verify ("verify"), uncommitted changes ("uncommitted"), deleted test
files ("deleted"), added lines that skip tests or silence checks ("weakened":
skip markers, `xit(`, `# type: ignore`, `eslint-disable`, `noqa`,
`--no-verify`), changed protected files ("protected", naming them), an
exhausted stop gate ("gate"), a blocker ("blocker", quoting BLOCKED.md), and a
missing report ("report").

## 14. Quality bar

- The acceptance suite passes: `python3 -m pytest -q tests`.
- A preparing agent that has never seen this project could follow SKILL.md
  and its references without asking anything.
- Messages printed by hooks and scripts say what is wrong and what to do next.
- Prose is plain: short sentences, reasons given, no capitals for emphasis.
